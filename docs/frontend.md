# Browser workspace

DroidShield serves a buildless browser interface at `/`, with same-origin assets at `/assets/app.js` and `/assets/styles.css`. Start the existing FastAPI application after applying migrations, open the application origin, and sign in with the provisioned email and password. The interface has no separate Node build, CDN, external font, or hosted service dependency.

The browser never receives or stores the session identifier. The server keeps it in an HttpOnly, SameSite=Strict cookie; the browser sends that cookie only to the same origin. A CSRF value is returned at sign-in/session restoration, held in page memory and required on writes. Reloading calls the session endpoint to restore access; closing the browser or signing out ends the local session, and the server expires it after the configured lifetime. Disconnect and expired authentication abort outstanding reads, clear rendered workspace data, and close resource dialogs. Protected application, analyst-evidence and report downloads use the session cookie and a temporary in-memory Blob URL. The client disables redirects and sends no Authorization bearer header. Report and evidence links carry only resource IDs. Deploy behind HTTPS when accessed beyond the local host.

## Visual system

The browser UI follows the sibling APISentinel dashboard's compact AppSec workspace language: a charcoal-navy canvas, quiet blue-gray panels, fine borders, mint primary actions, readable data tables, and restrained severity colors. APISentinel is a visual reference only; DroidShield keeps its own mobile-assessment workflows, API contracts, and records. Typography uses installed system sans-serif and monospace stacks, with no remote fonts, scripts, or image dependencies. Shared tokens and components in `web/styles.css` define page headings, cards, KPI values, tables, status badges, empty states, notices, right-side form drawers and controls so each workflow keeps the same visual hierarchy. Forms use two-column groups on wider screens and a single column in the full-screen mobile drawer. Status colors communicate workflow state and severity, while all data and counts remain API-backed. Desktop and narrow layouts share the same components, with responsive navigation, horizontal table scrolling, visible keyboard focus and reduced-motion support.

Record tables use a consistent `Action` column with an eye icon and `View` label. The action stays pinned at the right edge when a table scrolls horizontally. View opens a scoped, read-only details drawer from the right, with a record heading, state summary, grouped detail fields and a clear action footer; clicking its backdrop or Close dismisses it. The drawer can link to the full detail page. Existing actions such as Download, Verify and Record result remain alongside it where applicable. Read-only roles retain access to permitted view actions.

Every visible record table uses the shared APISentinel-style pager: the left side shows the current range and total, while the right side shows the current page and accessible Previous/Next controls. Each list keeps its own offset so nested project, assessment, finding, report, API and methodology tables do not move one another. Server-backed lists request a bounded page of 25 records; filters reset related pagers to the first page. Methodology coverage uses the same layout over its versioned in-memory case list.

Data tables retain the visible card or subsection title, expose a semantic caption for assistive technology, and use restrained teal/blue column accents, zebra rows and higher-contrast record text for quick scanning.

Static queueing, dynamic sessions and API baselines require their separately running workers. A queued record alone does not execute a scan. The UI sends the last observed revision for optimistic concurrency, and every POST mutation gets an idempotency key retained for retries of the same form values. An interrupted write is reported as an unknown outcome; the interface does not silently create a new request key for the same retry. A changed body receives a new key. Revision conflicts preserve edits for reconciliation.

The backend is authoritative for current role, ownership, workspace boundaries, authorization, artifact integrity, scope and lifecycle. Hiding an action is a usability aid, not an access control. Viewer sessions receive read-only controls. Sensitive configuration and lab connection details never appear in this interface.

## Form behavior and accessibility

Forms open in a right-side drawer on desktop and use the full viewport on mobile. The page remains visible behind the drawer for context. Fields are grouped, required fields are marked, browser-level format/length checks run before submit, and sanitized server validation locations link to inline errors. Company/Individual changes update the client name label while preserving its value. Optional blank contact values become null. Archive fields require a reason, and archival confirmation names the resource. Client private notes are not made editable from a redacted representation.

Directory and activity filters apply automatically: text fields use a short debounce, and selects refresh immediately. There is no Apply filters button. Each filter panel keeps Reset filters on a separate lower row aligned to the right; it is disabled when no filter is active. Filter values remain in the current page session, are sent only as supported API query parameters, and reset pagination to the first page after a change.

Save prevents repeated submission while a request is pending. Cancel and Escape check for dirty edits. Reset restores the original form values after confirmation. Long-running upload inspection exposes a pending state. Native modal dialogs provide drawer focus containment, Escape handling and return focus. The shell includes a skip link, semantic tables, labeled filters, reduced-motion styling, mobile navigation, status announcements and keyboard focus indicators. Record names, notes, descriptions, evidence and error messages are escaped before rendering; server-provided content is never evaluated as HTML or JavaScript.

Team & Access is hidden from non-administrator navigation and checks the current role before fetching its administrator-only endpoint. Its create/edit and session-revocation actions use the shared right-side drawer, same-origin CSRF protection and idempotency keys. New accounts are created disabled; password setup happens through the trusted local CLI before activation. The current administrator cannot revoke their own sessions from the member table, and password or token values are never displayed.

Workspace preferences are fetched only for administrators from the ADMIN-only settings endpoint. Administrators can edit the workspace name, recognized IANA display time zone, date format, default report template and optional report branding in the shared right-side drawer. Saves include the current revision and use same-origin CSRF protection; a conflict offers a reload of the latest saved settings. Secret values are never requested for editing or rendered: the page displays only server-provided configuration-presence status, which does not imply runtime readiness. Non-administrators receive no settings response and cannot open the edit action.

Active assessment and session details refresh every five seconds while the page is visible. Refresh pauses while a dialog is open. Leaving a page aborts its reads. All displayed timestamps use the browser's local timezone, which is explicitly shown in the page footer and Settings; authorization input labels indicate local time and values are serialized to UTC.

## Network and runtime observation forms

The API target form starts from an API assessment's exact requested HTTPS targets. Each endpoint has its own GET/HEAD method and expected-authentication checkbox; endpoint rows can be added or removed up to the backend's 20-endpoint limit. Authentication is Anonymous, Bearer, API key or Cookie/session. Authenticated methods require a primary protected reference, with an optional distinct comparison account. Selectors read only the current project's reference names and authentication kinds; there is no browser field for credentials, arbitrary headers, cookies or tokens. Changing the selected assessment reloads project-bound references. An API assessment needs no APK.

Targets include exclusions, a 1–120 requests-per-minute rate and required local-time start/end inputs serialized to UTC. The form checks the configured total-request budget across anonymous and account probes. The backend separately checks authorization, scope, window, secret ownership and runtime network policy. Target configuration is immutable: prepare a new assessment to change it after creation. Running the baseline requires the assessment's last observed revision and a review action. Active execution details refresh and expose cancellation; a completed run shows independent account statuses/sizes, response-comparison categories, verified TLS and header-presence observations. Bodies, raw headers and body digests are never rendered.

Frida and proxy scenarios appear only when the server explicitly returns their configured capability. The Frida view contains fixed native filesystem-open, socket-connect and DNS-lookup hook availability and counters; paths, addresses and call arguments are outside the response contract. Proxy observation shows its original approved allowlist plus indexed GET/HEAD status/TLS/size observations and bounded forwarded/blocked/failure counts. Other scenarios omit proxy fields. The UI explains that the app must trust the dedicated lab CA and that certificate pinning is not bypassed. Configuration flags do not establish worker or device readiness; the worker checks those controls before use.

## Analyst service delivery

Projects explicitly select Android or iOS. The identity field is an Android package ID or iOS bundle ID; authorization targets use `package:` or `bundle:` accordingly. The protected upload accepts APK, AAB and IPA. The interface states that AAB/IPA intake metadata is not full static security analysis, and APK engines remain the automated static path. Framework declarations, including Other for Kony/Volt MX, do not imply proven binary or runtime coverage.

An assessment can begin a manual engagement after the backend validates scope, current authorization, platform and artifact. The start form records the external environment, tool name/version and execution limitations. Methodology then records explicit results rather than inferring them from an engine run. Pass/Fail requires linked sanitized evidence; Fail also links a finding. The library covers secrets, cryptography, dependencies, local storage, authentication, tokens/OAuth, transport, BOLA/IDOR, API/business logic, Android/iOS platform interactions, privacy and resilience. Unrun controls remain visible. The user submits an execution summary before a distinct administrator reviews assessment completion.

Pending authorization records also accept one-at-a-time supporting PDF, PNG or JPEG files up to 8 MiB. Files are stored as private immutable objects, listed by safe metadata and downloaded only after current project-access and digest checks. The browser does not preview or render attachments; authorization verification remains a separate administrator decision.

Evidence is entered as bounded text or an 8 MiB PNG screenshot, with explicit sanitization acknowledgment, platform, tool/version, environment and tested artifact. Ordinary list/detail reads show metadata. Reading text or downloading a screenshot uses a separate authenticated, integrity-checked attachment request; screenshots are never rendered inline. Finding forms retain separate severity, verification and remediation. Non-informational findings ask for a CVSS vector; a server calculation supplies the validated score. Saving edits returns a finding to Unreviewed. A distinct administrator records Confirmed, False Positive or Needs More Evidence with a rationale. The browser does not expose Fixed as an edit option.

A mobile retest links a distinct application build, current authorization, the testing method/environment, new-build evidence and an observed result. An API-only retest instead uses the original release reference pinned from reviewed, pre-completion finding evidence and a distinct new release reference with matching new evidence; it requires no APK. Release references are analyst-declared deployment identifiers, not server-verified binary hashes. Its detail page presents original and new evidence in adjacent panels. A distinct administrator approves or rejects the evidence-backed outcome. To attach a new build, upload it through a separate draft assessment in the same project, then record new-build evidence from the original finding.

Reports are generated only from completed, human-reviewed assessments. The form asks for an executive summary, explicit methodology/limitations, template, branding identity, severities and evidence/remediation inclusion. A frozen snapshot appears for review; an administrator other than the author approves release before export becomes available. PDF/JSON export creation records an immutable file and checksum; a separate Download action fetches it with current authentication. Reports describe scope and framework coverage without asserting SOC 2, ISO 27001, HIPAA or PCI DSS certification.

Burp, Objection, jailbroken iOS devices and broader Frida/runtime analysis run in the analyst's separately authorized lab. The interface records their sanitized evidence and provenance; it does not label these tools as automatically executed. The existing configured Android observer and exact API baseline remain separately bounded automated options.

## Current limits

Team administration and safe workspace presentation settings are available to administrators. Self-service invitation/password setup, last-login tracking and notifications still require dedicated workflows. Workspace name, display time zone, date format, default report template and optional report branding can be edited in the browser; engine configuration and secret rotation remain server-managed. A successful scanner run produces unreviewed evidence and a Needs Review assessment; it does not mark a vulnerability Confirmed or Fixed. Full mobile assessments use the authorized manual engagement workflow, with tools, platform, environment, explicit limitations, recorded coverage, evidence and independent completion review. This does not orchestrate a complete automated pentest. API execution covers bounded exact HTTPS GET/HEAD baselines and test-account response comparisons; injection, fuzzing, OpenAPI execution, arbitrary request bodies and complete API vulnerability coverage are outside this workflow. Frida covers its fixed native observer, and proxy coverage depends on app routing and CA trust during the short session.

Reference selectors load accessible server pages, up to the API's documented maximum offset. They fail explicitly if that bound is exceeded. Client and project detail tabs use the related-record endpoints with client/project scope and independent server pagination; activity and overview counts come from the same scoped API records. Server-paginated directories remain the navigation entry points for larger workspaces.

## Verification

Run the dependency-free browser logic/security checks with a modern Node.js runtime (Node 22 or newer):

```sh
node --test tests/frontend.mjs
```

The tests cover untrusted markup escaping, safe routes and search serialization, explicit field allowlists, optional values, integer/date parsing, same-origin session requests, CSRF headers, bearer-header absence, redirect refusal, multipart boundaries, repeated idempotency keys, expired authentication, request correlation, field errors, navigation aborts and interrupted writes. Overview checks additionally cover the rolling trend range, severity breakdown, safe date handling, overdue-retest count and accessible daily table. Network UI checks additionally cover structured endpoint serialization, unsafe credential/query/fragment URL rejection, explicit runtime capability gates, fixed Frida/proxy counters, independent API account observations, review wording and raw-field exclusion. Distributed assets are checked for browser credential persistence and external executable content. Delivery checks also cover supported artifact extensions, strict boolean and evidence-list serialization, preserved Not Run coverage, hostile analyst text in the coverage/report review displays, and authenticated PDF downloads.

Browser verification on 2026-10-28 used a private disposable database and locally generated test-account references. The real API assessment/target forms, two endpoint methods, expected-authentication flag, secret reference selectors, UTC/local-time conversion, execution queue/cancel and tab-memory reconnect were exercised. A second baseline reached a separately started real worker and a trusted local HTTPS fixture: six actual requests produced anonymous 401 versus authenticated 200, HEAD zero-byte observations, verified TLS and persisted sanitized results rendered in the API evidence tables. No external target was contacted. Temporary credentials, fixture, app process and database were removed after the check. The current email/password cookie flow has integration coverage for session restoration, CSRF enforcement and logout revocation; browser UI automation was not run for this change. Backend runtime adapter tests separately establish configured Frida/proxy execution; frontend helper tests alone do not establish a lab's readiness.
