# Portfolio data and service scope

DroidShield tables and KPI values come from authenticated workspace APIs. The
portfolio video is a visual reference for density and style; it is not a source
of customer records or assessment results. The Client and Project directories
request aggregate metrics for the visible page only. The backend limits these
metrics to resources the current role can access.

## Local portfolio dataset

The local review workspace is generated by `scripts/seed_portfolio_demo.py`.
Its records and app binaries are fictional fixtures for UI review; the script
does not contact an external target, launch a device, or run a security scan.
It writes only to an isolated, migrated database and protected storage path
under `var/`, and refuses to overwrite a populated database or storage folder.

| Dataset | Records | State |
| --- | ---: | --- |
| Clients / projects | 100 / 120 | Fictional finance, healthcare, commerce and enterprise engagements |
| App artifacts | 258 | Generated APK, AAB and IPA fixtures; no client binaries |
| Authorizations | 120 | Historical, expired sample scope; never a current permission to test |
| Assessments | 480 | 200 completed manual examples; 56 each draft, awaiting-authorization, needs-review, failed and cancelled; no active queue |
| Analysis jobs / results | 28 / 0 | Cancelled sample records only; no worker result is fabricated |
| API targets / executions | 120 / 14 | Reserved `.example.com` targets with expired windows; execution rows are cancelled before any request |
| Dynamic sessions | 14 | Cancelled before device launch; no emulator or app was started |
| Findings / protected evidence | 456 / 656 | Completed assessments have reviewed examples; needs-review assessments keep candidates unreviewed; no findings are attached to pre-test or failed/cancelled assessments |
| Methodology executions | 1,440 | Pre-test, failed and cancelled assessments remain Not Run; completed/review examples contain version-pinned coverage records |
| Retests | 200 | Generated evidence records; only 17 findings are Fixed, each with an approved passing retest |
| Reports / snapshots / exports | 101 / 101 / 33 | Immutable, checksummed sample snapshots linked to completed assessments |
| Team users / audit events | 100 / 599 | Fictional workspace identities and safe action metadata |

Every organization, app, authorization, finding, evidence item and outcome is
fictional. The workspace title marks this as a synthetic dataset. Do not use
these records as client references or claim that the listed assessments were
performed. The seed command preserves the source database and requires a new,
empty target:

```sh
DROIDSHIELD_DATABASE_URL=sqlite:////absolute/path/under/project/var/portfolio-review.db alembic upgrade head
python scripts/seed_portfolio_demo.py --target-db var/portfolio-review.db --storage-root var/portfolio-review-artifacts
```

Expired authorization windows and cancelled, result-free API/Dynamic examples
are deliberate: the preview must not imply that a worker, external request or
runtime device ran. Scanner candidates and reports remain examples only; no
assessment result is a certification or a promise of zero false positives.

## Service coverage for real engagements

| Service | DroidShield data path | Boundary to communicate to a client |
| --- | --- | --- |
| APK static analysis | Protected upload → server-derived SHA-256 and metadata → isolated manifest/DEX worker; optional fixed MobSF adapter | Automated output is a candidate list, not a confirmed result. APK is the current full automated Android path. |
| AAB and IPA intake | Protected archive intake and bounded metadata extraction | AAB/IPA intake is not full bytecode analysis. Decompile and review through approved external analyst tooling and record coverage/evidence. |
| Android dynamic work | Authorized disposable emulator, bounded fixed Frida observer and controlled HTTPS GET/HEAD proxy scenario | Rooted physical-device workflows, Objection and broader Burp sessions remain analyst-run outside this worker. Pinning bypass is not provided. |
| iOS dynamic work | Manual engagement, device/tool provenance, test coverage and protected evidence | Jailbroken-device, Frida, Objection and Burp execution require the tester's authorized Apple lab; DroidShield does not automate iOS runtime testing. |
| Local storage and auth/session | Version-pinned manual cases for Keychain/Keystore, SQLite, preferences, plist, logs, cache, biometrics, JWT, OAuth/SSO and revocation | Record the exact test account, build, expected behavior and sanitized proof. Never add live secrets or production personal data to notes. |
| Backend API | Exact in-scope HTTPS GET/HEAD baseline with TLS checks and optional protected two-account comparison; manual BOLA/IDOR, authorization and business-logic coverage | The baseline does not send arbitrary methods/bodies or establish BOLA. Broader API testing remains manual and evidence-backed. |
| Platform and resilience | Coverage for deep links, intent/IPC, WebView, exported components, root/jailbreak, debugging, integrity and repackaging | Automated manifest indicators do not establish exploitability or complete anti-tamper coverage. |
| Code/dependency review | Assessment coverage and source/inventory evidence linked to the immutable app version | Supplied repository, framework internals and dependency advisories require analyst review and explicit scope. |
| Reporting and retesting | Frozen report snapshots, CVSS v4.0/v3.1, MASVS mapping, remediation priorities, independent approval, PDF/JSON exports and evidence-backed retests | Reports support audit evidence but do not certify SOC 2, ISO 27001, HIPAA, PCI DSS or app-store approval. Retest is performed only when included in the engagement. |

Current detailed limits and workflow requirements are documented in
[service delivery](service-delivery.md), [analyst workflow](analyst-workflow.md),
and [reporting](reporting.md).
